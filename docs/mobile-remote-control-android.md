# Android Remote-Control Shell

`packages/android` is the Android shell for ZCode's phone remote control. The first version does
not reimplement the ZCode Agent, the relay, or the RPC protocol — it hosts the existing `/remote`
mobile web remote-control page inside a native entry point.

## Entry points

- Paste or share a `https://zcode.z.ai/remote?...` link.
- Scan the remote-control QR code generated by the desktop app; when the code points at a
  self-hosted zcode-server, the app asks for confirmation and then saves and connects
  (see “QR scanning” and “Direct connection to a self-hosted zcode-server” below).
- Open via the `zcode://remote?...` deep link.
- Enter and save a self-hosted zcode-server address manually (see “Direct connection” below).
- The home screen keeps the last 5 remote links that opened successfully and lets you reopen
  them after an app restart. The list shows only the device name, host, and time; the full
  link is stored in the app's private `SharedPreferences`.

Release builds only allow `https://zcode.z.ai/remote`. Debug builds additionally allow
localhost and LAN `/remote` pages so a local Vite dev server can be tested on a real device.

## QR scanning

Scanning uses a CameraX preview with ML Kit Barcode Scanning. The scanner only recognizes QR
codes; whatever it reads is still validated by `RemoteControlUrlPolicy`: relay links, the
`zcode://remote` deep link, and links whose origin matches a saved direct server open right
away, as before.

Anything the allowlist rejects is then parsed as a direct-server address
(`DirectServerDraft.fromUrl`, pure JVM and unit-testable): only http/https, a root path, and a
query containing nothing but `?token=` are accepted; relay hosts (`zcode.z.ai`) and deep links
return null and always take the original path. When parsing succeeds the app shows a
confirmation dialog, “Save and connect to <host:port>?”:

- Confirm: `DirectServerStore.save` writes the normalized origin and the optional token, then
  the app connects via `buildConnectUrl` (still going through the `openRemoteUrl` allowlist —
  no second allowlist path is introduced).
- Cancel: nothing is written.

If both paths fail to parse, the QR is reported invalid and the WebView is never entered.

## Background stability

Once the remote page opens, the app starts a foreground service and keeps the screen on. The
foreground service lowers the chance that Android reclaims the process or tightens networking
in the background; it does not change the source of business truth. Reconnect and recovery on
the phone still rely on the existing web remote control's `web-remote-replayable` semantics,
bridge rebuilds, and task snapshot alignment.

The Android app never creates its own Agent runtime, local host, or SSH/WSL/Docker session.
The phone can only attach to a host that already exists in a desktop window.

## Direct connection to a self-hosted zcode-server

Besides the official relay (`https://zcode.z.ai/remote`), the shell can connect directly to the
user's own `@zcode/server` instance (`packages/server`, default port 3030). That instance serves
both the Web SPA (`ZCODE_WEB_STATIC_ROOT`) and the `/ws` channel, so this path needs neither the
relay nor a Z.AI account login.

The desktop app ships the same server — see
[docs/direct-server-desktop.md](./direct-server-desktop.md): the desktop main process
automatically runs a local direct server after startup (the token is persisted in
`~/.zcode/v2/direct-server.json`), and the remote-control dialog's “LAN direct connect” card
renders a `http://<lan-ip>:<port>/?token=…` QR code that this shell consumes through the same
save-and-connect path described above. Note that the card only has a web page to show when the
desktop is configured with `ZCODE_WEB_STATIC_ROOT`; without it the shell can still establish the
`/ws` connection but the WebView has no content (the desktop UI says so honestly).

- The launcher has a “Direct server” section: enter the server address (e.g.
  `192.168.1.10:3030`, `https://zcode.example.com`) and an optional access token (the server's
  `ZCODE_SERVER_AUTH_TOKEN`).
- Besides manual entry, a direct address recognized from a QR code (`DirectServerDraft.fromUrl`)
  goes through the same save-and-connect path after user confirmation, ending in
  `DirectServerStore.save` + `buildConnectUrl`.
- Server entries are stored in the app's private `SharedPreferences` (`DirectServerStore`):
  origin, display name, and token. Tokens sit at the same security level as the recent remote
  links; upgrading to EncryptedSharedPreferences is a follow-up.
- Connecting opens `<origin>/?token=<token>`: the server turns the token into an HttpOnly
  cookie (`zcode_lite_token`), and the SPA then opens the same-origin `/ws` channel.
- The URL allowlist gains one rule: in release builds a main-frame URL is allowed only when its
  origin exactly matches a saved server and the path is `/` (a `?token=` query is allowed for
  the cookie bootstrap). All other navigation rules are unchanged — the shell still cannot be
  used as a general browser; non-matching links go to the system browser.
- Release builds therefore enable `usesCleartextTraffic` (for LAN http servers). The security
  boundary on this path is the navigation allowlist plus the server token, not transport
  encryption; use https or Tailscale HTTPS when you need encryption in transit.

## Release builds and signing

- `applicationId`/namespace is `ai.zcode.mobile` (change it to your own reverse-domain id before
  publishing; the `zcode://remote` deep link does not depend on the applicationId).
- Release signing reads `packages/android/keystore.properties` (gitignored; template in
  `keystore.example.properties`) or `~/.gradle/zcode-android-release.properties`:
  `ZCODE_ANDROID_STORE_FILE`, `ZCODE_ANDROID_STORE_PASSWORD`, `ZCODE_ANDROID_KEY_ALIAS`,
  `ZCODE_ANDROID_KEY_PASSWORD`. The keystore file and the properties containing passwords must
  never be committed. When the configuration is missing, `assembleRelease` produces an unsigned
  APK instead of failing the build.
- Generating a keystore:

  ```bash
  keytool -genkeypair -v -keystore zcode-release.jks -keyalg RSA -keysize 2048 \
    -validity 10000 -alias zcode
  ```

- Artifacts: `./gradlew :app:assembleRelease` (APK, for sideloading) and
  `./gradlew :app:bundleRelease` (AAB, for store distribution). The first release keeps
  `isMinifyEnabled = false`; enabling shrinking is a follow-up.
